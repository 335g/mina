> [`docs/gitignore/loop/method.md`](../../docs/gitignore/loop/method.md) に運用マニュアル
> （コマンド・判定規則・落とし穴・LSP 直叩きプローブ）、
> [`docs/gitignore/loop/latest.md`](../../docs/gitignore/loop/latest.md) に最新結果と
> 次の課題設定がある。**新しいセッションはその 2 つを読めば次のループを回せる。**
> 本ファイルは計測器（L0）の仕様で、上の 2 つが参照する正本。

minas の目的は**エージェントのコスト低減**。その改善は「思いつきで直す」のではなく、
**課題設定 → 検証 → 考察 → 修正 → 効果確認**のループとして回す。このディレクトリは
そのループの**計測器と手順**を提供する。

## 2層のループ

| 層 | 道具 | 費用/時間 | 何を決めるか |
|---|---|---|---|
| **L0（内側）** | `l0.py` | 無料・数秒〜1分・決定論的 | どの仮説が**棄却されるか**。L0 で差が出ない仮説は L2 を回さない |
| **L2（外側）** | `../ab/ab.py` + `docs/benchmarks/` | 数十円/run・分単位・高分散 | 実LLMで**実際に安くなったか**（最終確認） |

L2 だけを回すと 1 仮説に数十分と数十円かかり、分散（nano n=5 で −5% 級は判定不能）で
判断もぶれる。L0 は「契約が要求する最小の往復数と出力量」を LLM 抜きで測るので、
**修正のたびに何度でも回せる**。両方回すのは L0 で差が出た仮説だけでよい。

## 指標（なぜこの4つか）

エージェントのトークン費用は往復ごとにコンテキスト全体を再送する構造なので:

```
cost ≈ Σ_{t=1..T} (C_0 + Σ_{i<t} o_i) = T·C_0 + Σ_i (T-i)·o_i
```

- `calls` — 往復数 `T`。**支配項**。`--hunks-stdin` のような往復削減がここに出る。
- `out_B` — 総出力バイト。ツール応答としてコンテキストに残る量。
- `equiv_B` — `Σ o_i + Σ (T-i)·o_i`。**序盤の大出力ほど高い**（後に何度も再送されるため）。
  全文ダンプが高いのは「大きいから」ではなく「**早く**大きいから」。
- `wall_ms` — 実時間。LSP ロード・`check` の settle 待ち・cargo を含む。
- `fails` — exit != 0 のステップ数。**迷い/回復の発生源**。1 増えると往復が 1〜3 増える。

迷い（hesitation）自体は L0 では測れないので、代理指標で捉える:

| 代理指標 | 見る場所 |
|---|---|
| 契約が要求する最小往復数（`calls`） | L0 — 契約が N 回を強制するなら全エージェントが N 回迷う |
| 失敗・拒否のステップ数（`fails`） | L0 |
| cold での無言の誤り（空応答 + exit 0） | L0 `--cold` |
| 最初の一手の種類・再読回数・skill 参照回数 | L2 `ab.py` の audit log |

## ループの回し方

1. **課題設定** — 仮説を**指標ペア**で書く。悪い例:「check を速くする」。
   良い例:「編集→検証の往復で `check` を `cargo check` に替えると、`calls` は同じで
   `wall_ms` が X→Y、`fails` が 1→0 になる」。**受理条件と棄却条件を先に書く。**
2. **検証（L0）** — `python3 tools/loop/l0.py -f <flow> -v`。仮説はアームとして足す
   （`FLOWS` に 1 エントリ）。ここで `calls`/`equiv_B`/`fails` に差が無ければ**棄却して次へ**。
3. **考察** — 差を `calls` / `out_B` / `equiv_B` / `wall_ms` に分解して帰属させる。
   差が期待と逆なら、それは計測器か仮説の欠陥。原因を書く。
4. **修正** — 一度に 1 つの仮説だけ。修正は**共通経路 1 箇所**（呼び出し側に散らさない）。
5. **効果確認** — L0 を再実行し、主要な変更だけ L2 を 1 本回す。
   結果は `--log` で `docs/benchmarks/agent-loop-log.md` に追記する（**棄却結果も消さない**）。

```console
$ python3 tools/loop/l0.py                       # 全フロー
$ python3 tools/loop/l0.py -f verify -v          # フロー絞り込み + ステップ別内訳
$ python3 tools/loop/l0.py --cold                # LSP ワークスペースロード前（cold 税）を測る
$ python3 tools/loop/l0.py -f verify -n "仮説: …" --log
$ python3 tools/loop/l0.py --selftest            # 計測器自体の健全性（daemon 不要）
```

`L0_MINAS` / `L0_MINAD` でバイナリを差し替えられる。既定は `target/debug/` が
あればそれ（自己ビルドを測る）、無ければ PATH。結果 JSON は `tmp/loop/`（gitignore）、
耐久記録は `docs/benchmarks/agent-loop-log.md`。

## 計測器の作り（信頼できる数字のための規則）

- **アームごとに専用 daemon**: 各アームは専用 `TMPDIR`（= 専用 socket）で `minad serve` を
  起動する。`minas info` の前後差分がそのアームだけの計測になる（グローバル daemon と混ざらない）。
- **fixture は毎回生成**: アームごとに新しい作業ディレクトリ。状態の持ち越しが無い。
- **warm / cold を分ける**: 既定は「LSP がワークスペースを読むまで待ってから」測る（契約費用）。
  `--cold` は起動直後（cold 税）。cold には**無言の誤り**（空応答 + exit 0）が乗るので、
  cold でしか出ない失敗は「契約の欠陥」として課題に上げる。
- `check` の settle 待ちのように**非決定な step は複数回測る**。1 回の観測で結論を出さない。

## 既知の限界

- fixture が小さい。`cargo check` が現実のクレートより桁で速いため、
  **L0 の `wall_ms` は実プロジェクトに外挿しない**（傾向の検出が役割。規模の確認は L2）。
- `calls`/`equiv_B` は fixture の規模に依存しない（契約の形で決まる）ので、外挿してよい。
- 1 アーム 1 回の観測。`equiv_B` は決定論的、`wall_ms` は揺れる。
- `C_0`（システムプロンプト等の固定費）は測らない。アーム間で同じなら比較に影響しない。
