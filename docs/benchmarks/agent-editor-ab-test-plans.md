# エージェント向けエディタ AB テストプラン（実LLM）

> **目的**: agent-editor-performance-considerations.md の「未検証の最重要項目」である
> **実 LLM による総合 A/B 比較**を実施するためのテストプラン。
> 範囲 read・拒否理由・コンテンツ解決型の各手段の「有効/無効」を、同一タスク・同一モデルで対比し、
> トークン・時間・成功・試行回数を定量する。
>
> **対象外**: expected_text による事故（破損・修復工程）比較はユーザー指定により実施しない。

## 0. 共通事項

### 0.1 実行基盤（ハーネス）

- **LLM**: opencode ゲートウェイ（`api.opencode.ai`、`OPENCODE_API_KEY` 認証）。`opencode run -m <model>` で疎通確認済み（gpt-5.4-nano / gemini-3.5-flash-lite が応答）。
- **エージェントループ**: 独自ドライバ（Python または dev02 を拡張）。モデルに「ツール＝mina CLI」を渡し、`session get --lines` / `session apply` / `session edit` / `session exec` をサブプロセスで実行。API 応答の `usage`（input/output tokens）を記録。
- **手段の有効/無効を「ツールセットの差」で制御**: 同一モデル・同一タスクに対し、露出するツールだけを変える。これでモデル自体の賢さを変数から排除する。
- **隔離**: 各 run は独立した作業ディレクトリ＋isolated daemon。`pkill` で前回 daemon を落としてから開始。

### 0.2 統計的な誠実さ

- 小標本（各 arm 5 回推奨、コスト次第で 3 回最低）→ **中央値＋IQR** を報告し、平均±分散は添えない。
- 有意性は Mann–Whitney U かシンプルな「差の方向が全 run で一致」で判断。p 値は付さない（小標本で誤解を招く）。
- 外れ値（タイムアウト・モデルの明らかな脱線）は除外して記録。
- モデルは両 arm で同一・同一シードの同一プロンプト文面を使う。

### 0.3 成功判定の共通化

各タスクは「正しさ」を機械的に検証できる終状態を持つ（コンパイルが通る・grep で期待増減・テストカウント一致）。成功= 終状態を達成、失敗= 上限ステップ内に未達。

## テスト 1: 範囲 read（`--lines`）のトークン/速度削減

### 仮説
「同一タスクで、全文 read より範囲 read（`session get --lines`）の方が、完了までの**総入力トークン**と**所要時間**が少ない（同時に読む量＝入力トークンを削減）。」

### 背後メカニズム（理由）
- P1/Q1 実測: 全文 203KB(≈50,871tok) ↔ 範囲 1,464B(≈366tok) = 99.3%削減。
- 総入力トークン ≈ Σ各 read のトークン。範囲 read は全体から必要な区間だけを読むので、累積入力が減る。
- 読む量が減るとプロンプトが短く→生成速度も速い（主にトークン削減の副次効果として速度も測る）。

### 実ケース（タスク）
- 対象: 実在っぽい中規模 Rust ファイル（約 700〜800 行、`tmp/` に生成）。関心領域が**ファイルの深部（600 行目以降）**にある。
- タスク: 「構造体 `Server`（700 行付近）に `read_timeout: Duration` フィールドを追加し、その `Default` 実装と、コンストラクタ・1箇所の使用（800 行付近）を更新せよ。更新後 `cargo check`（対象クレートのみ）が通ること。」
- 関心領域は上部の import と深部の定義・使用に散在するよう配置する。

### 2 つの Arm（同一タスク・同一モデル）
- **Arm A（範囲 read）**: read ツール = `mina session get --lines start:end` のみ。grep 相当も mina/grep で行指定可能。
- **Arm B（全文 read）**: read ツール = `mina session get`（全文スナップショット）のみ。

### 制御（同一にするもの）
- ファイル内容・タスク文面・モデル・最大ステップ(≤20)・許可ツール（apply/edit は同一の `session apply` を両 arm で使用）。
- **差は read ツールだけ**。

### 計測
| 指標 | 定義 |
|---|---|
| 総入力トークン | タスク中の全 API input tokens の和 |
| 総出力トークン | 同上 output tokens |
| 所要時間 | 開始→成功/上限まで |
| read 呼び出し回数 | read ツールの実行回数 |
| 成功率 | 終状態達成 / 試行数 |

### 手順
1. ファイル生成 → タスク文面を固定化。
2. Arm A を 5 回、Arm B を 5 回実行（交互に、モデル偏り回避）。
3. 各 run の usage を記録。中央値で比較。
4. 報告: 「範囲 read は完了トークンを X%、時間を Y% 削減（中央値）。成功回数 Z/5 vs W/5」。

### 期待解釈
- **範囲 read が優位**: 仮説支持。→ デフォルトの read 契約として範囲指定を推奨。
- **差が小さい**: モデルが全文を読まずとも済む（grep/対象の絞り込みを先にやる）場合、効果が縮小。→ 実運用で「どのタスク種で効くか」の境界を示す。

## テスト 2: 拒否理由（C1）による回復コスト削減

### 仮説
「編集が拒否されたとき、**具体的な拒否理由（expected/found/範囲）がある場合の方が、回復までの試行回数・トークンが少ない**。」

### 背後メカニズム（理由）
- F8/C1: 拒否メッセージがそのまま行動指示になる。`expected "…", found "…" at [lo,hi)` があれば、盲目的全文再読をせず対象範囲だけ読み直せる。
- このプロジェクトの局所実測（模擬）: 対象行 read 545B vs 全文再読 39,901B = 98.6%。実モデルのリトライ回数では未検証。

### 実ケース（タスク）
- 対象: 小さな Rust/Python ファイル（複数フィールドを持つ構造体、40〜60 行）。
- タスク: 「`Config` 構造体の `timeout` フィールドを `5000` から `30000` に変更し、その使用箇所も追随せよ。」
- **drift 注入**: エージェントが最初の apply を終えた直後、ハーネスが**別の非関連行**（例: 別フィールドにコメントを1行追加）を外部から書き込む。これにより次回 edit の expected_text が不一致になり拒否が発火する。

### 2 つの Arm（同一タスク・同一モデル・同一 drift）
- **Arm A（具体理由）**: 拒否応答に `expected text mismatch: expected "...", found "..." at [lo, hi)` を載せる（現行 mina の C1 仕様）。
- **Arm B（汎用理由）**: 拒否応答は `edit rejected: document changed; re-read and retry`（理由・範囲なし）。

### 制御
- drift の注入タイミング・内容は両 arm で同一。モデル・最大ステップ同一。read は両 arm とも `session get --lines` を使用（片方だけ不利にしないよう統一）。

### 計測
| 指標 | 定義 |
|---|---|
| 回復までのステップ数 | 拒否発火→終状態達成までのツール呼び出し数 |
| 回復に要した入力トークン | 拒否後から達成までの input tokens |
| 拒否後の再読バイト数 | read ツールが返したテキストの総量 |
| 成功/失敗 | 上限 ≤25 ステップ内で達成か |

### 手順
1. ファイル + task + drift を固定。
2. Arm A×5 / Arm B×5 を交互実行。drift は「各 run で初回 apply 成功後」と固定。
3. 拒否からの回復コストを中央値で比較。

### 期待解釈
- **A が B より回復ステップ/トークン少**: 仮説支持。→ C1 の拒否理由は「エージェントの回復コスト」を直接下げる。
- 差が小さい: モデルがそもそも全文再読をしない・または汎用理由でも素早く再 read する場合。→ 拒否理由の追加情報の価値境界。

## テスト 3: コンテンツ解決型（apply）vs 位置指定（edit）の編集成功率

### 仮説
「同一タスクで、**コンテンツ解決型 `session apply`（old/new 文字列）の方が、位置指定 `session edit`（start/end char インデックス）より編集成功率が高く、試行回数・トークンが少ない**。」

### 背後メカニズム（理由）
- J1/B1: dev02 で「apply は位置計算ゼロで初回成功。位置指定は get→範囲計算→edit の3ステップ手書きでミス源」を観察。Aider ベンチでも search/replace→unified diff で成功率 26%→59%。
- 位置計算はモデルの苦手分野。apply は文字列一致なので、計算誤差による失敗が構造的に消える。

### 実ケース（タスク）
- 対象: 2 ファイル（約 80〜150 行）。`USD` という定数/変数が 6〜8 箇所に出現、メソッド名 `price()` を `amount()` にリネーム（定義＋呼び出し 3 箇所）。
- タスク: 「`USD` を `JPY` に、`price()` を `amount()` にリネームし、全箇所更新せよ。`cargo check`（対象のみ）が通ること。」

### 2 つの Arm（同一タスク・同一モデル）
- **Arm A（コンテンツ解決型）**: edit ツール = `session apply <path> <old> <new>`（必要なら `--hunks-stdin`）。old/new は文字列で指定。
- **Arm B（位置指定）**: edit ツール = `session edit`。JSON で `start`/`end`（char インデックス）を自前計算して指定。checksum は `session get` から取得。

### 制御
- read は両 arm とも `session get --lines` に統一（同じ読む能力にする）。モデル・最大ステップ同一。**差は edit ツールだけ**。

### 計測
| 指標 | 定義 |
|---|---|
| 編集成功率（正しさ） | 全リネームが正しく適用され `cargo check` が通った run 数 / 試行 |
| 編集の試行回数 | edit ツール呼び出し数（拒否・失敗含む） |
| 総入力トークン | タスク全体の input tokens |
| ツール呼び出し総数 | read+edit+check の合計 |

### 手順
1. 2 ファイル生成 → タスク固定。
2. Arm A×5 / Arm B×5 を交互実行。
3. 成功率・試行回数・トークンを比較。

### 期待解釈
- **Arm A が成功率高・試行少**: 仮説支持。→ コンテンツ解決型をエージェント向けデフォルトの編集正面入口として維持（B1 階層化の実証）。
- 位置指定も同程度: モデル（今回）は位置計算が得意、または小タスクでは誤差が顕在化しない。→ 「タスク規模でどれだけ差が出るか」の境界を報告。

## 4. 実施順序と所要コスト（概算）

| 順 | テスト | run 数 | モデル | 概算トークン | 備考 |
|---|---|---|---|---|---|
| 0 | ハーネス検証（1タスク1arm、模擬） | 1 | gpt-5.4-nano | 数十K | 配線確認 |
| 1 | テスト1（範囲read） | 5+5 | gpt-5.4-nano | 数百K | 安価モデルで先に |
| 2 | テスト3（apply vs edit） | 5+5 | gpt-5.4-nano | 数百K | 成功率中心 |
| 3 | テスト2（拒否理由） | 5+5 | gpt-5.4-nano | 数百K | drift 制御が肝 |
| 4 |（任意）上位モデルで再現 | 3+3×各 | gemini-3.5-flash / claude-sonnet | 高 | 頑健性確認 |

- 各 run は小タスク（ファイル ≤800 行・ステップ ≤25）なので、コストは 1 run あたり数十〜数百円規模。計測前に「まず 1arm ずつ」で立ち上げ、モデル・ツール配線を確認してから本数に入る。
- レポートは docs/ 配下に結果を追記する（成功/失敗、中央値、限界）。

## 5. リスクと対策

- **opencode API の実エンドポイントが取得できていない**: 現状 `opencode run` 経由のみ疎通確認。→ 実行時は「独自ループ（raw endpoint）」か「opencode run をサンドボックス駆動」のいずれかで実装。raw endpoint が不透明なら、`opencode run` を bash サンドボックスで使い、ツールセットの差はプロンプト＋ツール wrapper の出し分けで制御する（フラジャイルなので優先対応）。
- **モデルの非決定性**: 同一 seed でも揺れる。→ 各 arm 複数回・交互実行・中央値報告。
- **drift 注入タイミングの揺れ**（テスト2）: 「初回 apply 成功直後」で固定し、注入はハーネスのみが行う（エージェントから見て外部編集）。
- **コスト超過**: まず安価モデル(gpt-5.4-nano)で全体を通し、有意な差が出たものだけ上位モデルで再現。
