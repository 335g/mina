## テスト1: 範囲 read（ネイティブ Read の offset/limit を代用）

※ opencode ネイティブ Read（offset/limit）を mina `--lines` の代用とした。同一メカニズム
（必要な行だけ渡す）。タスク: 700行の Rust 風ファイル深部の struct にフィールド追加。

| arm | 入力トークン中央値 | コスト中央値 | 成功率 |
|---|---|---|---|
| A 範囲read | 18,262 | $0.0088 | 4/4 |
| B 全文read | 37,086 | $0.0112 | 4/4 |
| **差** | **−50.8%**（全 run で A<B の完全分離） | **−21.1%** | — |

## テスト3: コンテンツ解決型（apply）vs 位置指定（edit）— mina shim 強制

**ハーネス**: tools/ab/。opencode を bash 専用 agent（native read/edit 無効）にし、
read は `mread`（=`mina session get --lines`）、edit は `medit`（A=`mina session apply` /
B=`mina session edit` 位置指定 JSON）に強制。コンプライアンス（shim 経由・直接 mina 呼び出し無し）を監査で判定。
タスク: f1.rs/f2.rs で `USD→JPY`、`price()→amount()` を全箇所リネーム（実ファイル変更あり）。

| arm | 成功率 | billed トークン中央値 | コスト中央値 | 観察 |
|---|---|---|---|---|
| A apply（内容指定） | **3/5** | 14,140 | $0.0076 | 適用は1回で通り、トークン低。失敗2件はモデルの取りこぼし（7回適用後に残り） |
| B edit（位置指定） | **0/5** | 70,764 | $0.0446 | **5.0倍** | **5.9倍** |

B の失敗様態（位置計算の帰結）:
- 拒否地獄: 全試行が拒否（rejects=7,8）→ 位置または checksum が実物と合わない。
- **誤位置の静かな適用**: edits=7 成功（rc=0）なのにファイルがほぼ無変更（JPY が 1 つも無い）—
  位置がずれたまま expected_text の範囲もずれて「正しくない場所への正しい内容」が適用される。
- 脱落: 非準拠 run ではファイルを消去（bash で rm）する挙動も 2 回観測（NC として除外）。

**解釈**: J1/B1 の実測確認。位置指定は「成功しない（拒否）」だけでなく「**成功したかのように
誤位置へ適用する**」危険があり、コストも 5〜6 倍。内容指定 apply は成功 3/5（失敗は適用
ミスではなくモデルの編集ツール使いこなし）。→ エージェント向け正面入口は apply（内容指定）
で正しいというハーネス実測の裏付け。

## テスト2: 拒否理由（C1）具体 vs 汎用 — ヌル結果

タスク: cfg.rs の `timeout 5000→30000`・`max_retries 3→5`。**ドリフト注入**: 最初の編集成功直後に
ハーネスが外部で `max_retries: 3,`→`max_retries: 4,` を書き換え、次の編集を強制的に拒否させる。
A: 拒否メッセージは実物（`NOT FOUND: "max_retries: 3,"`）。B: shim が汎用メッセージ（対象文字列なし）。

| arm | 成功率 | billed 中央値 | コスト中央値 | 拒否後回復 |
|---|---|---|---|---|
| A 具体理由 | 5/5 | 9,304 | $0.0039 | 再読→適用で1歩 |
| B 汎用理由 | 5/5 | 10,237 | $0.0046 | 再読→適用で1歩 |
| 差 | — | A が 9.1% 少ない | A が 15.2% 安い | ほぼ同 |

**解釈（正直なヌル結果）**: 小タスク（〜20行）・単一の拒否・**範囲 read が既に使える**構成では、
汎用メッセージでも「再読→対象を特定→修正」に 1 歩しかかからず、具体情報の優位は小さかった
（トークン差 9%、有意と判定できる規模ではない）。C1 の価値が顕在化するのは「ファイルが大きく
全文再読が高い」「拒否が反復する」状況で、本タスクでは再現されなかった。

## テスト4: LSP 意味 rename（`mrename`）vs apply — ざっくり均衡

**ハーネス**: typescript-language-server を shim 内部で stdio LSP として立て、`textDocument/rename`
（意味解析）の WorkspaceEdit をファイルへ直接適用する `mrename <path> <old> <new>` を新設。
タスク: rename.ts で `USD→JPY`・`price→amount`（定義＋呼び出し）。
A = `medit`（apply ループ）、B = `mrename`（LSP）。n=5/arm。

| arm | 成功率 | billed 中央値 | コスト中央値 | wall |
|---|---|---|---|---|
| A apply（内容指定） | 5/5 | 8,184 | $0.0035 | 18〜36s |
| B LSP rename | 5/5 | 7,739 | $0.0026 | 29〜35s |
| 差 | — | B が **5.4% 少ない** | B が **25.7% 安い** | ほぼ同じ |

**解釈（誠実な収束）**: この小タスクでは apply も LSP も**ほぼ横並び** — apply は既に安い
（5回の部分置換＋3回の read）ので、LSP の意味解析による優位は顕在化しなかった。
コスト−26% は output 削減（LSP は 1 ツール呼び出しで全箇所）由来。
LSP の優位が拡大するのは「出現箇所が多く・クロスファイル・構造ノイズがある」タスクで、
今回は未計測。加えて LSP は**位置指定 arm（t3-B）の失敗様態（拒否地獄・誤位置の静かな適用）
を構造的に排除する** — この価値は本テストの均衡結果に表れていない（比較軸が違う）。

### T4 実装上の発見（ハーネス品質）
- rust-analyzer 1.98 は `--stdio` フラグ廃止（素起動が stdio LSP）。また rename が
  `content modified` で拒否される（未解決）→ **typescript-language-server に切替**。
- mrename の最初の実装バグ（wrapper の余分な引数）により、モデルが shim を迂回して
  python で直接編集した run が「成功」扱いになっていた → bypass 検出（sed/python 等）を
  強化し、非準拠 run を除外。**ツールが壊れているとモデルは黙って代替手段に逃げる**、
  という観察（compliance 監査の必要性）。

## テスト5: LSP rename vs apply — 出現多数・複数ファイルで LSP が優位

**設計**: T4 の限界（小タスクで均衡）を踏まえ、「出現箇所多数・クロスファイル」領域で再計測。
フィクスチャ: 3 ファイル（utils/data/main.ts）、`USD` x12・`price` x9（計21箇所、複数ファイルに分散、
import/export で結合）。A=apply ループ（`medit`、1回1出現）、B=`mrename`（LSP、1シンボル1呼び出し
で全参照）。n=5/arm。

| arm | 成功率 | billed 中央値 | コスト中央値 | wall |
|---|---|---|---|---|
| A apply（内容指定） | 2/5（3回は出現取りこぼし） | 24,528 | $0.0149 | 65〜168s |
| B LSP rename | **5/5** | 12,583 | $0.0064 | 38〜75s |
| 差 | — | B が **48.7% 少ない** | B が **57.0% 安い** | B が速い |

**解釈**: 規模が実用的になると明確に LSP が勝つ。(1) apply ループは 20〜24 回の適用を
要求され、**出現を取りこぼす**（A-3/4 は price を 1 箇所残す、A-5 は USD と price を残す）—
数え漏れ・同一出現への再適用が発生。(2) LSP は 1 シンボル 1 呼び出しで全参照を網羅し、
取りこぼしが構造的に起きない。(3) トークン・コストは約半分、wall も短い。
→ **t4（小規模）は均衡、t5（出現多数・複数ファイル）では LSP が優位**。実務の rename は
後者の領域に属する。「apply を正面入口に、rename は意味解析ツールに」という使い分けが
コスト最小・成功率最大の組合せになる実測根拠。

## テスト6: `mina skill` 参照の有無 — 判断には差なし・トークンは増える

**設計**: ツールセットは両 arm 同一（mread / medit / mrename / mcheck 全部あり）。タスクは T5
と同じ多出現リネーム（LSP が正解の領域）。違いは**「skill 索引/詳細への参照手段の有無」だけ**。
A = 指示文に「`mina skill` で索引、`mina skill <topic>` で各ガイドを参照せよ」を追記。
B = skill に言及しない。どちらも「どのツールでリネームするか」は指示しない。n=5/arm。

| arm | 成功率 | billed 中央値 | コスト中央値 | mrename 採用 | skill 参照 |
|---|---|---|---|---|---|
| A skill あり | 5/5 | 17,541 | $0.0071 | 5/5 | 1〜3回 |
| B skill なし | 5/5 | 11,060（準拠 run） | $0.0057 | 5/5 | 0回 |
| 差 | — | A が **+58.6%** | A が **+24.6%** | 差なし | — |

**解釈（誠実なヌル〜逆方向結果）**: このタスクでは skill は判断を変えなかった。
両 arm とも全 run が mrename を選んで成功 — ツール説明（"language-aware rename (all references,
one call)"）が既に「正しい経路」を伝えており、skill の判断表は付加情報にならなかった。
skill 参照自体は 300〜500 トークン×1〜3回＋検証 read の増加で、**A は 59% 多くトークンを
消費した**。

**示唆**: (1) 判断は**ツール説明（常時ロード・無料のカード）**に載せるのが最安で確実。
(2) skill（オンデマンドの参考書）の価値は、ツール名・説明から自明でない部分 — exit コードの
意味・dirty/保存・拒否からの回復・positional を避ける理由（t3）— にあり、本タスク（名称から
結論が自明）では発現しない。(3) 副産物として B-2 が非準拠（直接編集 bypass=1・renames=6）で
も成功 — ツールが十分ならモデルは多少の迂回でも完遂できるが、監査除外は継続必要。

## テスト7: 拒否回復の大規模再検証（600行・ドリフト）× skill

**設計**: T2 のヌル（小タスク・単一拒否・全文再読が安い）を改善し、600行の生成ファイルに
8つのターゲット（TARGET_k = 100+k）を分散配置。タスク: 各値を +1 に。ドリフト: 最初の編集
成功直後にハーネスが `TARGET_5 = 105` を `1050` に外部書換 → 記憶ベースの old 文字列が
合わず拒否（NOT FOUND）。両 arm とも**同じ実メッセージ**。A のみ `mina skill` を参照可能
（bin/mina は skill 専用ラッパーに制限 — 直接 session 呼び出しは shim 迂回として除外）。
n=5/arm（準拠 run A=4, B=4）。

| arm | 成功率 | billed 中央値 | コスト中央値 | 拒否後 recover | skill 参照 |
|---|---|---|---|---|---|
| A skill あり | **4/4** | 19,186 | $0.00975 | 全 run 正常（TARGET_5=106 へ適応） | 0〜3回 |
| B skill なし | 3/4 | 15,848 | $0.00940 | 1件誤回復 | 0回 |
| 差 | A が上 | A が **+21.1%** | A が **+3.7%** | — | — |

**失敗の内訳（正直）**: B-3 は拒否後の回復で `let TARGET_5 = 1050;` を `1051` に変更 —
ドリフトされた値を「新しい基準」と誤解する**意味論のスリップ**であり、ツール使いの失敗ではない
（skill の errors トピックが防げたとは言い切れない）。

**解釈（T6 と同系の結果）**: 大規模化しても skill 参照は判断・回復成功率に**明確な上乗せを
示さず**、トークンは +21%（参照コスト＋検証 read）。回復手順（再読→修正→再試行）は
モデルがメッセージと範囲 read から自然に導出でき、skill の記載が付加価値を生まなかった。
**「skill の価値は行為が自明でない領域に限定」** が T6/T7 で一致。未検証の価値仮説は
「positional 等の**ツールの罠**を skill が回避させるか」（t3 ではモデルが自発的に位置指定を
試みていた）— これが残課題。

## テスト8: positional の罠回避 × skill — 罠が自発されない（二重のヌル）

**設計**: 残課題だった「skill がツールの罠（positional）を回避させるか」を直接計測。
両 arm とも位置指定ツール `medit`（char オフセット JSON）と内容指定 `mapply` を中性記述で提供し、
タスクに**明示的な行番号ヒント**（line 31: …line 191:）を仕込んで位置指定への誘因を作った
（チケットの行番号指示に似た現実的な罠）。A のみ `mina skill` 参照可（edit トピックが
「never compute positions」を明記）。タスク: 5 か所の値を +1。A は準拠 6 run、B は 5 run。

| arm | 成功率 | billed 中央値 | コスト中央値 | positional 使用 | skill 参照 |
|---|---|---|---|---|---|
| A skill あり | 6/6 | 16,144 | $0.0065 | **0/6** | 0〜2回 |
| B skill なし | 5/5 | 10,038 | $0.0049 | **0/5** | 0回 |
| 差 | — | A が **+60.8%** | A が **+32.7%** | 差なし | — |

**解釈（誠実なダブルヌル）**: (1) **罠はどちらの arm でも自発されなかった** — 行番号ヒント＋
位置指定ツールの存在があっても、モデルは一貫して内容指定 mapply を選んだ（t8 全 run で pos=0）。
t3 の位置指定失敗は「強制された」あるいは「代替が無い」条件で起きるのであって、自発的な
デフォルトではない、ということが示された。(2) ゆえに skill の警戒文（edit トピックの
"never compute positions"）は**引き金が無い状態では効果を発揮しようがない** — A/B とも同一の
選択・同一の成功で、skill 参照分のトークン（+61%）だけが乗った。

**副産物（ハーネス改善）**: skill 用に公開した `mina` が「直接 `session apply` を試みる」挙動を
誘発（A の多数で観測）。ラッパーが拒否（exit 1）すれば無害であるため、**「拒否された直接
呼び出し」を bypass 勘定から除外**する判定を実装（refused カウント）。「壊れた/制限された経路を
叩く」のはモデルの自然な探索であり、実害の有無で判定すべきという知見。

**T6〜T8 の統合結論**: `mina skill` は、判断が（a）ツール説明から自明（T6）、（b）モデルが
自然に導出（T7）、（c）そもそも引き金が無い（T8）のいずれの領域でも付加価値を出さず、
参照コストだけが乗る。**skill の価値領域はさらに狭く、現状の実測では確認できていない。**
skill は「擬似コード的知識（exit コードの全レンジ・保存契約・非自明なツール）」の参照用として
維持し、判断の大部分はツール説明と mini 本体の契約（exit 0/1/2・拒否メッセージ）に担わせる
設計が実測と整合する。

## テスト9（M2・2026-08-29）: mina 本体の `session rename` vs apply — Rust で T5 を再現

（apply ループ）、B = `mrename`（`mina session rename` のパススルー shim）。モデル・計測は
T1〜T8 と同一（gpt-5.4-nano、opencode DB）。n=5/arm。

| arm | 成功率 | billed 中央値 | コスト中央値 | wall 中央値 | ツール使用 |
|---|---|---|---|---|---|
| A apply（内容指定） | **3/5**（2 run が `price` を 1 箇所取りこぼし） | 30,597 | $0.0155 | 80s | 24 edits |
| B `session rename`（mina 本体） | **5/5**（準拠 4/4） | **11,752** | **$0.0060** | **35s** | 2 rename 呼び出し |
| 差 | — | **−61.6%** | **−61%** | −56% | — |

- A の失敗様態は T5 と同一: `price_left=True` — apply ループは出現を数え漏らす（

- B は 1 シンボル 1 呼び出し（2 回の rename で 24 箇所を網羅）。取りこぼしが構造的に起きない。
- t9-B-4 は非準拠（bypass>0、直接編集を試みた）だが成功 — 「ツールが十分なら迂回しても
  完遂できる」という T4 の観察と一致（準拠 run のみで中央値を算出）。
- **M2 の意味**: 検証で最良だった LSP rename を製品化（`session rename`）した結果、
  ハーネスの専用 shim（tsserver）と同等以上（T5: −49%/−57% → M2: −61.6%/−61%）の優位を
  Rust・実 rust-analyzer で再現。ツール説明の使い分け判断（skill の rename トピック）は
  そのまま本体の機能に裏付けられる。

## テスト11（M3・2026-08-30）: 汎用2ファイル機能追加 — naive 契約 vs mina session 契約

T1〜T10 は read 効率・edit 契約・rename 機能を個別のミクロタスクで測った。T11 は
LSP を使わない実務タスク（「読む→理解→直す」）を 1 本にし、**ツール契約全体**（全文 read
＋無検証置換 vs 番号付き範囲 read＋検証付き apply）を対比する。フィクスチャは単体で
`cargo check` が通る Rust クレート（config.rs / main.rs、各 ~600 行）に `max_conns`
フィールドを追加する 5 編集（struct フィールド・Default・decode・validate・main の env 読込）。
モデル・計測は T1〜T10 と同一（gpt-5.4-nano、opencode DB）。n=5/arm。

- 仕掛け: 600 行全文 read のトークン圧迫（~5k tokens/回）/ drift 注入（最初の成功編集直後に
decode 構文行を外部書き換え — 両 arm の次編集の anchor が古くなる。回復コストが差になる）。
- A-5 の失敗様態: 編集 21 回・拒否 5 回の迷走から decode/validate/main に到達できず
  cargo FAIL — t5/t9 で見た「apply/置換の回復ループで迷子」と同一パターン。
- B は全 run 成功。drift 後の拒否（rejects 1〜2）から範囲再読で素早く回復。
- B-4 は非準拠（bypass=1、直接編集を試みた）だが成功 — t9-B-4 と同一の観察（準拠 run で中央値）。
- **M3 の意味**: read 効率・edit 検証・drift 検知の効用が、LSP なしの汎用タスクでも
  契約全体のトークン −40.9%・コスト −43.4%・成功率 4/5→5/5 として再現された。
  個別ミクロ測定（T1 −50.8% / T3 成功率 0/5→3/5）の方向と一致。

## 検証の限界（すべてのテストに共通）

- 単一モデル（gpt-5.4-nano）・小標本（n=4〜5）。上位モデルでの再現は未実施。
- T1 はネイティブ Read の代用、T2〜T8 は mina/LSP shim 強制（bash 専用 agent）。
  bash は完全な shell なので「絶対に shim を使う」強制はできず、非準拠 run（直接 mina
  呼び出し・sed/python 直編集）は監査＋bypass 検出で除外した。
- T2 はタスク規模の制約によるヌル結果。C1 の優位が測れる設計（大ファイル・複数拒否）は未実施。
- T7 は大規模化したが、「拒否メッセージが既に文字列を名指しする」「範囲 read が使える」ため、
  具体情報の付加価値が薄いまま。skill の真価仮説（positional の罠を回避させる）は未検証。

## 総括

- 実装面（mina）: 範囲 read・拒否理由・dirty 警告・CLI 世代・contract 表 — 実装済み。
