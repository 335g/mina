# エージェント向けエディタの性能・コスト考察

> **位置づけ**: これは**考察（設計上の推論）**であり、**実検証（統制された測定）は未実施**。
> 個別の実機観察・既存実測値（dev-feedback.md の P1/Q1, M1/N1 など）を「参考」として引用するが、
> 「手段X がトークン/速度/試行回数をどれだけ改善するか」を A/B 等で**定量的に比較した検証は行っていない**。
> 各項目には本文中で **[考察]** / **[実機観察あり]** / **[定量的実測あり]** を明記する。

## 1. 目的と前提

エージェント用エディタの性能・コストは、人間用と同じ指標で測れない。人間にとって無料のものが、エージェントには課金される。

| 観点 | 人間用エディタ | エージェント用エディタ |
|---|---|---|
| 画面の探索・編集 | 無料・無意識 | **トークン課金** |
| 読み書き1往復 | 無料 | **レイテンシ＋トークン** |
| 失敗→やり直し | 無料・即時 | **試行回数＝コスト（再読・再計算の往復）** |

よってエージェント用エディタの設計目標は、以下を**最小化**することに帰着する。

1. **1回の読み書きで渡す量**（＝トークン数）
2. **1動作の所要時間**（＝速度）
3. **失敗してやり直す回数**（＝試行回数）

このうち **3（試行回数）は総コストに対して乗算で効く**ため、テコとして最も大きい可能性がある（後述）。

## 2. トークン数削減（1回の読み書き量の最小化）

> コストモデル: 総トークン ≒ Σ(各往復でエディタが渡す量)。渡す量はほぼ「読む量＋返す量」。
> → 「全文を渡さない」「結果をコンパクトに返す」が直接効く。

| 手段 | メカニズム | 効果の出方 | 検証状態 |
|---|---|---|---|
| **範囲指定 read**（行/範囲だけ読む） | 全文を渡さず必要な区間のみ返す。読むバイト量がトークンに比例 | 必要な部分だけを対象にするほど線形に削減 | **[定量的実測あり]** P1/Q1: 2000行中11行のみ＝18,893B(≈4,723tok)→110B(≈27tok)≒**99.3%削減** |
| **局所検証 edit**（old文字列で照合） | 内容一致で差し替えるため、編集前後の「全文読み直し」が不要 | 1回の編集で全文再読の往復を丸ごと1往復分削減 | **[定量的実測あり]** P1/Q1 の結論（edit側の単独定量は未実施） |
| **コンテンツ解決型を正面入口に**（位置計算を排除） | 位置や checksum をモデルが管理しない。位置計算ミス→再読→再計算のループが消える | 試行回数（後述の3）とトークンの両方に効く | **[実機観察あり]** J1: dev02 で位置計算ゼロ・初回成功。B1（Aider 26%→59% は他文献） |
| **応答を機械可読 JSON に**（描画装飾を返さない） | 画面用の装飾・全文ではなく `{applied, checksum, edits, generation}` のみ | 返すトークンを最小化 | **[実機観察あり]** L5/M3: 1行JSONをツール結果に載せるのが正解と判明 |
| **バッチ編集（1コマンド複数置換）** | 複数編集を1接続に丸め、N回分の接続・Open・Saveを1回に | トークン＋速度の両方に効く | **[定量的実測あり]** M1/N1: 3置換 単発×3=0.261s vs バッチ1回=0.087s ≒**約3倍**（速度側） |

**考察の要点**: トークン削減の本質は「**全文再読の往復をどれだけ消せるか**」。
範囲read・局所検証・バッチが揃うと、編集1ループの入出力を最小にできる。
※「トークン削減が実際の課金・所要時間にどれだけ寄与するか」の総合 A/B は**未実施**。

## 3. 速度向上（レイテンシの最小化）

| 手段 | メカニズム | 検証状態 |
|---|---|---|
| **常駐 daemon で状態を保持** | 起動・再読込・再解析を毎回やらない。状態は差分だけやり取り | **[実機観察あり]** ADR-0005/0006（daemon-client 分割・StateSnapshot IPC） |

## 4. 失敗率低減（試行回数の最小化）— 本節は詳細

### 4.0 なぜ失敗率が最優先か（コストモデル）

総コスト ≒ **1回あたりのコスト × 試行回数**。トークン削減・速度向上は「1回あたり」を下げるが、
失敗率低減は「**試行回数**」という**乗数**を下げる。乗数を下げる方が、分母が大きいほど支配的になる。

さらに失敗は「再読→再計算→再投稿」という**遅い・高トークンの往復を伴う**ため、
失敗1回の実コストは成功1回より大きい。**失敗を減らす＝最も高コストな往復を消す**ことでもある。

**ただし**: 「失敗率低減が総コストをどれだけ改善するか」の**定量比較は未実施**。
以下は、フェイルモード（何がどう壊れるか）→ 防御（どの手段が防ぐか）→ メカニズム（なぜ効くか）→ ギャップ（何を防げないか）で整理した考察である。

### 4.1 フェイルモードと防御の全体像

| # | フェイルモード（何が壊れる） | 直接の防御 | 層 |
|---|---|---|---|
| F1 | **陳腐化**: 読み取り後に別編集で文書が変わる（stale） | checksum（全文）検証で拒否 | 検知 |
| F2 | **位置・内容の想定ずれ**: モデルが位置を誤る／両実装が同一の誤りを共有 | expected_text（局所）検証 | 検知 |
| F3 | **適用の非原子性**: 複数hunkの途中失敗で部分適用 | 原子 bunch（全か無か） | 検知 |
| F4 | **undo 分解**: replace を delete→insert の2段階にし、undo が不自然になる | 単一トランザクション編集（ファサード） | 予防 |
| F5 | **サイレント能力ギャップ**: 旧daemonが新フィールドを黙殺し検証が効かない | 能力ネゴシエーション／世代開示 | 予防 |
| F6 | **結果の曖昧さ**: 「空の成功」と「説明付きゼロ結果」を区別できない | 説明付きゼロ結果を返す | 回復 |
| F7 | **リトライ非冪等**: 部分成功の再実行で壊す／再試行に注意深い状態参照が必要 | 冪等 noop＋原子 bunch＋出口コード分類 | 回復 |
| F8 | **拒否情報不足**: 拒否理由が次の行動にならず盲目的再読ループ | 具体的拒否理由（期待/実値の断片） | 回復 |
| F9 | **大ブロック置換の破壊**: 大きいoldを1回で置換し範囲を巻き込む | 小分け置換／全体書換の使い分け（運用） | 予防 |

層の意味:
- **検知層**: 間違った編集を「適用前に」見つける（破損させない）
- **回復層**: 失敗しても「安く・安全に」やり直せる（試行回数を増やさない）
- **予防層**: そもそも失敗を起こさない（位置計算・共有誤り・黙殺を根絶）

### 4.2 各防御の詳解

#### F1: checksum（全文）検証 — 【検知層】

- **メカニズム**: 編集適用時に、読み取り時点の全文 checksum（UTF-8 バイト列の FNV-1a 64）と現在の全文を突き合わせ、不一致なら stale として拒否。*「どこかが変わった」* を全体として検出する。
- **なぜ効くか**: エージェントの「読んだ後の文書」前提を無効化する。別セッション・別ツール・外部編集が入っても、壊れた状態へ書き込まない。
- **ギャップ**: 「変わった」ことは教えるが「どこが・どう」は教えない。**全体として変わらなければ**（＝局所の位置ずれ等）検出できない。
- **検証状態**: **[実機観察あり]** G2・フィードバック5（stale拒否の動作確認）。「拒否により試行回数が減った」の定量は未実施。

#### F2: expected_text（局所）検証 — 【検知層】

- **メカニズム**: 編集対象の範囲に「ここにあるはずの文字列」を指定し、その場の実テキストと照合。不一致なら拒否。*「この場所が想定と違う」* を局所的に検出する。
- **なぜ効くか（最重要の考察ポイント）**:
  1. **位置がずれていても内容で検出できる**。座標ではなく中身を突き合わせるため、offset が1文字ずれても実テキストが不一致になって引っかかる（**[実機観察あり]** フィードバック18: checksumは一致するのに expected_text が検出）。
  2. **共有誤りの連鎖を断ち切る**（**[考察]** フィードバック4-2 の観察に基づく）: daemon とエージェントの**両実装が同じ誤った前提を共有**していると checksum も expected_text も「一致」してしまう。しかし、各自が**独立した fresh read** に基づく expected_text を持てば、共有誤りは不一致として顕在化する。**「両側が同じ間違いを犯す」ケースこそ、この検証の本当の価値**。
- **ギャップ**: エージェントが誤った old 文字列を渡し、それが別の場所に偶然存在すると誤ターゲットし得る（範囲と併用で緩和）。また検証が機能しているか自体は別途 F5 で担保が必要。
- **検証状態**: **[実機観察あり]** G2/G3・フィードバック17〜19。「発動して事故を防いだ回数」の長期集計は未実施。

#### F3: 原子 bunch（全か無か）＋順次適用保証 — 【検知層】

- **メカニズム**: 複数hunkの1プロセス適用。途中hunkが不一致なら**全体を未保存・exit code で拒否**し、ディスク無変更。適用順序は配列順に保証。
- **なぜ効くか**: 部分適用状態が作れないため、クライアント側のロールバック考慮が不要になる。失敗＝「全部やり直し」で、復旧ロジックが消える。
- **ギャップ**: 原子性は「1回の適用呼び出し」内のみ。クライアントが別ツール呼び出しを複数行う場合は契約外。
- **検証状態**: **[実機観察あり]** L1〜L5 / M2（仕様確定・実機確認）。「部分適用が実際に防がれた回数」の定量は未計測。

#### F4: 単一トランザクション編集（undo 分解の防止）— 【予防層】

- **メカニズム**: 「編集を適用する関数」と「undo可能に記録する関数」を一本化したファサードが、`(Document, Transaction)` を返す。replace が単一 Transaction になり、`invert` 1回で完全復元できる。
- **なぜ効くか**: replace を delete→insert の2段階で書くと undo が2段階になり中間状態が観測できる。ファサードはこの「正しい手順が API から自明でない」誤り（**[実機観察あり]** フィードバック4・7〜12）を**構造的に防ぐ**。
- **ギャップ**: 各クライアントがファサード経由でない別経路（直接プロトコル操作）を使うと効かない（「1本の道」原則に依存）。
- **検証状態**: **[実機観察あり]** 実機で編集→undo の原文復元を確認（フィードバック8）。「失敗回避回数」の定量は未実施。

#### F5: 能力ネゴシエーション／世代開示 — 【予防層】★最重要事故級

- **メカニズム**: 接続時に daemon のビルド世代・機能レベル（例: expected_text 対応有無）を開示し、クライアントが「検証が効いているか」を検知可能にする。黙って無視しない（silent-ignore を可視化）。
- **なぜ効くか（考察）**: 検知層（F1/F2）は「正しく動く daemon を前提」とする。旧 daemon が新フィールドを**黙殺**すると、検証なしで適用され、ファイル破損が起きても status=None の成功応答で**検知不能**になる（**[実機観察あり]** 報告1-1〜1-5: expected_text 黙殺→Cargo.toml/main.rs 破損2回）。これは業界の既知の事故クラス（LSP#174 / K8s#71623 / Chromium Sync）と同型。**「黙って無視は必ず事故になる」**。
- **ギャップ**: daemon 側の世代開示は対処済みでも、**CLI バイナリ側の世代確認手段**（I4）は未対応。再ビルド後にリリースバイナリが古いまま、という同型事故が残る。
- **検証状態**: **[実機観察あり]** 第2ラウンドで事故2回・D1→#27 で対処。「検知により事故がX回防がれた」は予測（[考察]）、回顧的実測は事故2回のみ。

#### F6: 「空の成功」と「説明付きゼロ結果」の区別 — 【回復層】

- **メカニズム**: 範囲 read で終端超過時など、空文字列を返す代わりに原因を言語化して返す（例: `(no lines in 3000..3100: file has 2000 lines)`）。
- **なぜ効くか**: 「そこに何もない」のか「何も返せなかった」のか区別できないと、エージェントは次の行動を推測して無駄な再試行をする。原因付きなら**次行動（範囲の絞り込み）が根拠を持つ**。
- **ギャップ**: read 側は対応済み（dev02）だが、minae 本体の session get / apply 側の同型対応（Q3）は保留。
- **検証状態**: **[実機観察あり]** R1（dev02で実装・確認）。「試行回数削減」への寄与は**[考察]**（定量未実施）。

#### F7: 冪等リトライ（noop＝正常完了）＋出口コード三値分類 — 【回復層】

- **メカニズム**: (1) new==old の noop を正常完了として扱う → 同じ old/new の再試行が自然に冪等になる。(2) 出口コードを 0=成功 / 2=検証拒否（再試行可能）/ 1=入力エラー（再試行不要）に分類し、JSON パースなしで分岐を決定的にする。
- **なぜ効くか**: 失敗時、エージェントは「無条件に再試行してよい」と決め打ちできる（状態参照・前処理不要）。部分適用の恐れは F3 の原子 bunch が除去済みなので、安全性を失わずにリトライを単純化できる。出口コードにより、**JSON を解釈しなくても**「再試行すべきか」が分かる。
- **ギャップ**: 冪等性・原子性は単一適用呼び出し内の保証。呼び出しをまたぐ重複はクライアント側の責務。
- **検証状態**: **[実機観察あり]** N2/L3/L4（仕様挙動の確認）。「リトライ成功率」への寄与は**[考察]**（定量未実施）。

#### F8: 具体的拒否理由（期待/実値の断片を返す）— 【回復層】

- **メカニズム**: 拒否時に「どこがどう違うか」を載せる。例: `expected text mismatch: expected "NOPE", found "LINE ONE" at [0, 8)`（先頭 ~40 文字、切れたら `…`）。
- **なぜ効くか**: 拒否メッセージが**そのまま次の行動指示**になる。具体的な「期待値 vs 実値 vs 範囲」があれば、モデルは**全文再読せず**に「対象範囲を読み直せばよい」と判断できる。盲目的な「全文再読→再投稿」ループ（失敗1回の実コストを肥大させる）を削る。
- **ギャップ**: 断片化（先頭40文字）のため、ずれが範囲の後方にある場合情報が足りない可能性。長文の粒度設計は実装判断。
- **検証状態**: **[実機観察あり]** C1 / G2 / I2 / K2（エラー文が行動指示として機能・エージェントは定型1文で済んだ）。**「拒否時の再読・再試行がどれだけ減ったか」の定量は未実施**。

#### F9: 小分け置換 vs 全体書換の使い分け — 【予防層】（運用）

- **メカニズム**: 構造的・全ファイル波及の変更は全体書換、局所的な変更は小さな置換を複数回。機械的 sed 的置換の複数回適用は避け、括弧バランス検証・バックアップ・コンパイラエラー頼みの反復修正を併用。
- **なぜ効くか**: 大きい old ブロックを1回で置換すると範囲を巻き込み実装を消し去る（**[実機観察あり]** フィードバック4-3/11m）。ブロー半径を小さくし、検証＋文法チェック＋コンパイラで失敗を局所化・復旧可能にする。
- **ギャップ**: これはエディタの仕様ではなく**エージェント（人間/モデル）側の使い方の原則**。ツールが強制できない。
- **検証状態**: **[実機観察あり]** 事故と運用ルール化の実績。定量予測はしない（運用手順のため）。

### 4.3 フェイルモード×防御の相補性（考察の要）

| 軸 | checksum（全文） | expected_text（局所） | 役割の分担 |
|---|---|---|---|
| 検出対象 | *どこかが変わった* | *この場所が想定と違う* | 全体 vs 局所 |
| 陳腐化（F1） | ○ | 部分 | checksum が主 |
| 位置ずれ（F2） | ✕ | ○ | expected_text が主 |
| 共有誤り（F2） | ✕ | ○（独立read前提） | expected_text が主 |

**補完性の要点**: checksum は「安い全体検証」、expected_text は「正確な局所検証」で相補的。
ただし検知層（F1/F2）は「検証が正しく動くこと」を F5 に依存するため、**検知層の上に予防層（F5）が必須**。
回復層（F6/F7/F8）は失敗を「安く・安全に」するもので、検知・予防層の外側で試行回数を守る。

## 6. 次に検証すべきこと（考察に基づく提案）

失敗率低減の効果を実証するには、以下の統制した測定が必要（すべて未実施）。

1. **拒否理由の有無による試行回数比較**: 同じ編集失敗を「具体理由あり/なし」で提示し、エージェントの再読・再試行回数を比較。
2. **expected_text 有無による事故・再試行比較**: 検証あり/なしで同一タスクを実行し、破損回数・修復工程数を比較。
3. **能力ネゴ「検知できる/できない」の事故比較**: 旧daemon混在シナリオで、検知可能な場合の停止までの工程数を比較。
4. **実LLM接続での総合測定**: dev02 等の実エージェントを実LLMに接続し、タスク完了までのトークン・時間・試行回数を、各手段の有無で比較。

この節にある手段はすべて**合理的なメカニズムに基づく考察**であり、導入可否の判断には上記の測定（特に「失敗率低減の総コストへの寄与」）が必要である。
