# Command/DocumentEdit split: selection-coupled vs position-addressed operations

The wire protocol distinguishes two operation surfaces. `Command` is the selection-coupled surface: it reads and may change the shared Selection, and is what the interactive TUI (via the Keymap) and agents driving the TUI (`session exec`) send. `DocumentEdit` is the position-addressed surface: insert/delete/replace at explicit character ranges that neither read nor change the Selection, sent by headless clients (`session edit`) that want to edit a document without being hostage to the TUI's cursor. The alternative — one shared command type with positional variants plus a convention that the TUI only uses the selection-based ones — was rejected: it leaves two valid ways to edit (selection-based and position-based) expressible by the same client, an ambiguity that degrades into whichever is more convenient to call. Splitting the types makes the boundary structural: the TUI cannot express a DocumentEdit, and a DocumentEdit cannot disturb the cursor. Both surfaces share the transport (NDJSON over the local socket), the snapshot response, and the Transaction machinery (undo groups, dirty, LSP sync).
