# Undo groups close on leaving Insert and on client disconnect

An UndoGroup — a set of Transactions reverted by a single undo — spans exactly one Insert session: it opens when the editor enters Insert mode and closes when it leaves Insert (to Normal or Select), or when the owning Client disconnects while in Insert (which also returns the editor to Normal). The alternative — closing only on Insert→Normal — leaves the group open through Select transitions and, worse, through client churn: because the daemon and its History are persistent (ADR-0005), an unclosed group merges edits from different sessions into one undo unit, silently destroying undo granularity (edits from a previous session vanish on a single undo).

Connection-scoped groups were initially rejected for v1 — under the effectively-one-client model a daemon-side boundary seemed sufficient. The documented primary workflow (agent-driven editing with a human TUI intervening) broke that assumption (HIGH-1): a one-shot agent connection ending while the human's Insert session was open closed the group and reset the mode to Normal, and an agent edit merged into the human's open group. Groups are therefore owned per connection: the Client whose `SetMode(Insert)` opened the group is its owner; only the owner's disconnect closes it, and a write from any other Client closes it first (last write wins — a single UndoGroup never contains edits from different Clients, because conflicting writes serialize instead of interleaving). Ownership is tracked daemon-side (no protocol change): group open/close stays daemon-driven, so the group scope does not need to be explicit in the wire types. A future multi-client model (multiple interactive Views) can revisit by making group scope explicit in the protocol.
